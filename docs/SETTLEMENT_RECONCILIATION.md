# Durable settlement reconciliation

`packages/clob/settlement-journal.ts` records settlement lifecycle evidence, **not collateral balances or current positions**. It cannot sign, broadcast, retry, enable HTTP trading or activate Fuji custody. The matcher journal and settlement journal are distinct single-writer histories; an offchain provisional match is not a canonical fill.

## Intent and transaction identity

Persist `recordIntent` before submitting anything. Identity binds local/Fuji chain, nonzero deployment ID, settlement contract, expected pair ID, both EIP-712 order hashes, fill size/price, submitting sender and transport nonce. Intent IDs are deterministic SHA-256 digests; they are not Ethereum order hashes. Transport nonce zero is supported. A sender/nonce cannot be reserved for a different intent, even after restart, and a transaction hash cannot be attached to two intents. An expected pair ID cannot be reused for another intent unless its previous attempt was canonically reverted. Orders with any unresolved intent are paused: changing the transport nonce or predicted pair ID cannot bypass unknown-outcome reconciliation.

`recordBroadcast` records an already submitted transaction separately; a hash alone exposes no fill. Replacements are explicit identities for the same intent/sender/nonce, with at most 64 recorded candidates. Reconciliation checks prior candidates too: a replacement hash does not prove the original transaction was dropped. This module never automatically submits or resubmits an unknown transaction. Recording a hash is not submission authorization.

The expected pair ID is a strict check, not a reservation. If concurrent permissionless settlement advances the onchain pair counter, the receipt must be reconciled explicitly against the actual event/contract state; no mismatched pair is silently credited and no automatic second fill is sent.

## Confirmation and restart

An injected read-only reader supplies receipts, canonical head and canonical block hashes. Every candidate receipt must have exact identity and status, and its actual transaction sender/transport nonce must match the persisted intent; confirmations must meet the journal's immutable policy. A matching fill log from another transaction sender or nonce cannot resolve this intent's unknown submission. A successful receipt still needs exactly one matching `MatchedFill(uint64,bytes32,bytes32,uint128,uint128)` event from the exact settlement contract, with the expected hashes, pair ID, fill size, price, transaction and block/log identity. Reverted, pending, unavailable, malformed, mismatched and reorged outcomes remain distinct. The canonical head hash is checked again before final acceptance.

Reconciliation is serialized. Caller inputs and asynchronous reader payloads are copied. Canonical block changes or unavailable evidence remove the fill from confirmed output until resynchronization. **Opening an existing journal downgrades every historical non-unknown intent to unknown and requires fresh canonical reconciliation**; replay alone cannot expose a current confirmed fill. This includes an intent with no recorded hash: a crash may have occurred after dispatch but before persisting the hash. Such an intent remains paused until an operator reconciles sender/nonce and actual transactions; it is not permission to submit again. A successful recheck may update confirmations or downgrade if the canonical head rolls back. Callers must continue reconciling: a previously observed confirmation is not an everlasting finality guarantee.

`confirmedFills()` reports validated fill events only. It is not a current-position ledger. `readCanonicalPosition` reads actual settlement metadata and canonical vault margins at one pinned block, verifies vault/deployment/module identity and rechecks both providers' block hashes after reading. Never-used IDs reject; fully closed positions are distinct from active ones, and mismatched ledger state or a reorg rejects the snapshot. Funding, partial/full closes and liquidation update these actual contract views, not a duplicate offchain balance. These are **current-canonical, not policy-confirmed** position snapshots: the helper reads the latest block and does not return a block source timestamp or enforce a minimum-confirmation policy. Do not feed them into freshness-gated confirmed matcher capacity, stamp them with wall-clock read time or use them to enable reduce-only/strategy execution. Phase 4 must add source-block timestamp/age and policy-confirmed-block selection before that integration. The existing live service remains unavailable rather than presenting these local development records as public positions.

## Matcher and feed outcome bridge

`SettlementOutcomeBridge` connects the actual matcher and settlement journals in trusted process code. Construction checks Fuji chain, settlement contract and the explicitly expected deployment ID. `reconcileTrade(tradeId, intentId, at)` verifies both canonical order hashes, long/short direction, owners, size/price and supported vanilla-limit flags, then asks the settlement journal for fresh canonical reconciliation. No caller-supplied status can confirm a fill through this API. A trade is permanently bound to its first intent; new intents cannot silently retry a reverted/unknown provisional match.

The matcher durably records the resulting status before returning sequenced `settlementOutcome` events. Only confirmed/reverted outcomes release pending-match capacity; pending/unknown/reorged outcomes retain or restore it. Terminal evidence is invalidated before awaiting a new chain read. Orders are not requeued on revert, and fills never create a duplicate position ledger. Unsupported flags cannot release reduce-only capacity against stale position snapshots. Terminal trade identities remain in bounded history for possible reorg downgrades; reaching 8,192 retained trades stops further matching rather than silently dropping evidence. Unresolved admission remains bounded at 4,096 matches. Existing pre-outcome command hashes remain compatible with matcher-journal replay; the journal is not reset or migrated.

`MarketDataFeed` validates status transitions and authoritative pending counts, including outcomes for trades older than its recent 128-trade window. Malformed/conflicting deltas freeze the client for resynchronization. `startMarketData(...).reconcileSettlement(...)` is trusted in-process only: it publishes a fresh coherent WebSocket snapshot after reconciliation, even on errors, so intervening timer/producer updates cannot reorder receipt deltas. Public HTTP mutations and `/ready` remain `503`; no signer, broadcast, activation or live public admission is introduced. If a reconciliation fails after a local write, consumers must resynchronize from the authoritative snapshot rather than assume no mutation occurred. On restart, operators must reconcile all bound trades before relying on historical capacity; opening a matcher journal alone is not chain verification.

Local tests use real generated EIP-712 signatures, durable journals and a real loopback WebSocket, but mocked chain observations. They cover both terminal outcomes, pending/unknown/reorg downgrades, restart, replay hash compatibility, older trades, unsupported flags and fail-closed public endpoints. They are not public fills or a hosted trading backend.

## RPC adapter

`packages/clob/settlement-reader.ts` uses installed viem clients to decode actual receipt ABI bytes, not a caller-supplied success flag. Receipt and canonical providers must have the correct chain, nonempty matching pinned runtime code and matching onchain deployment ID; checks continue after startup. It fetches the immutable transaction to verify hash, target, actual sender and safe transport nonce, validates receipt/block/log identity and rejects removed or malformed matching logs. Receipt-not-found returns unavailable, not dropped/filled. Other provider errors propagate for conservative reconciliation.

Callers must configure independently qualified providers and verify deployed code against their reviewed manifest. The adapter pins the observed runtime code and compares providers; this is not independent source-code verification or a public activation gate. A malicious or colluding RPC provider can lie. The two clients may point to the same local node for tests; that is not public multi-provider canonicality evidence.

## Durability and checks

Settlement journal engine schema **2** requires actual transaction sender/nonce proof. Engine-1 journals are refused without truncation or reset; automatic migration is not provided. Preserve and reconcile every old intent/transaction before a separately tested migration—never start a fresh journal to bypass unknown outcomes.

The bounded append-only journal has an exclusive writer lock, hash/sequence checks, strict replay validation, fsync-before-state acknowledgment and directory fsync at creation. Missing state, identity/policy changes, corruption and incomplete tails fail closed; no automatic truncation/reset/lock theft occurs. Unknown writes poison the writer and retain the lock, including during startup reconciliation checkpointing. Recover only after confirming the old writer is stopped and reconciling the journal and canonical chain. Hash chains detect corruption and unrehashed edits, not a malicious filesystem owner.

OpenCode drafted the journal and its initial 15 tests. Pi review added nonce-zero/identity isolation, restart revalidation, repeated confirmations/head rollback, original-after-replacement and head-change safeguards with regression tests, plus a real-byte RPC adapter and pinned current-position reader. Twenty-five journal and eight adapter/position tests pass under `npm run test:clob`; TypeScript typechecking passes. Deterministic reader mocks are unit-test fixtures, not public settlement evidence.
